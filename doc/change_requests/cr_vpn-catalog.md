## 1. Проблематика

### 1.1. Контекст

Выборочный VPN на роутере и машинах работает по спискам сайтов: через VPN идут только записи каталога, остальной трафик идет напрямую. Нужен отдельный репозиторий - единственное место, где каталог хранится и формируется. Потребители (навыки других репозиториев) забирают каталог сами и преобразуют в свои форматы.

Требования пользователя:

- репозиторий называется vpn-list, приватный;
- в репозитории только каталог и все, что с ним связано: навык обогащения и актуализации;
- каталог наполняется с нуля, без затравки из старых списков;
- внешние источники - только дообогащение: добавляют записи, не удаляют;
- ручные дописывания разрешены в любой момент и скриптами не удаляются;
- строгой синхронизации с внешними каталогами нет;
- переопределений «всегда-в» и «всегда-напрямую» нет: каталог - список того, что идет через VPN, остальное напрямую.

### 1.2. Текущее состояние

- Папка vpn-list создана, каркас - копия хаба project_standards 4.15.0: полный пакет doc/standards, hub-навыки glob-*, пустые doc/specs и doc/change_requests, шаблонные AGENTS.md и README.
- Git не инициализирован. CLAUDE.md удален (в производных репо не ведется); .gitignore и .gitattributes подлежат восстановлению при git init (project_standards.md, раздел 06.01).
- Прежнее решение - списки внутри навыка rtr-vpn-setup в arch_desktop_setup - заменяется связкой «репозиторий каталога + навыки-потребители» (CR cr_vpn-three-part-split.md в arch_desktop_setup).

### 1.3. Следствия бездействия

- Списки остаются внутри навыка другого репозитория: их нельзя переиспользовать и версионировать отдельно.
- Нет единого источника истины: потребители собирают наборы независимо.

## 2. Варианты решения

### 2.1. Репозиторий каталога со своим навыком обогащения (рекомендация)

- Описание: в vpn-list живут data/lists/catalog.json и data/skills/vpn-list-update. Навык обогащает каталог из внешних источников (только добавление), актуализирует даты и версию, проверяет целостность. Потребители забирают JSON сами.
- Достоинства: один источник истины; данные отделены от потребителей; переиспользование любым агентом; история в git.
- Ограничения и риски: потребители зависят от стабильности формата каталога; формат фиксируется в README как контракт.

### 2.2. Каталог без навыка

- Описание: в репозитории только catalog.json, обогащение ведет навык из arch_desktop_setup.
- Достоинства: репозиторий минимальнее.
- Ограничения и риски: логика каталога живет в другом репо; навык не переносим вместе с данными.

### 2.3. Каталог с экспортом и доставкой

- Описание: навык дополнительно генерирует форматы потребителей и раздает их.
- Достоинства: потребителям проще.
- Ограничения и риски: репозиторий данных обрастает чужой ответственностью; любой агент способен сам разобрать JSON, экспорт избыточен.

Рекомендация: 2.1.

## 5. Цели и non-goals

Цели:

- единый каталог списков VPN с обогащением add-only и версией yymmdd;
- навык обогащения и актуализации внутри репозитория;
- задокументированный контракт формата для потребителей.

Non-goals:

- экспорт в форматы потребителей и доставка на роутер и машины;
- проверка «работает через VPN» - второй этап навыка;
- наполнение затравкой из старых списков.

## 6. Риски и критерии приемки

Риски:

- форматы внешних источников меняются: навык сообщает о неудачной загрузке и не портит каталог;
- широкие подсети раздувают каталог и туннель: ограничение маски и числа записей при обогащении.

Критерии приемки:

- catalog.json валиден, все группы присутствуют, версия yymmdd;
- повторный enrich не удаляет и не дублирует записи, ручные правки сохраняются;
- validate ловит дубли и битые записи;
- README содержит контракт формата.

3. Тесты на живых источниках
4. Git init, приватный репозиторий на GitHub, push, тег yymmdd - после успешных тестов
