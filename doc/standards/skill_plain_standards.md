# Стандарт оформления plain-навыков AI-агента. Версия 4.15.0

Документ описывает правила создания и оформления plain-навыков (плоских навыков) - специализированных инструкций для AI-агента. Plain-навык - один плоский файл `.md`; термин «внутренний формат» пакета означает этот же формат. Второй формат пакета - навык формата Anthropic: каталог с `SKILL.md` (`skill_anthropic_standards.md`). Является дополнением к `doc/standards/project_standards.md` и применяется поверх него. Все требования основного стандарта остаются в силе, кроме случаев, явно описанных в данном документе.

Навыки не заменяют `AGENTS.md`, `CLAUDE.md` и `doc/standards/project_standards.md`. В навыках - только узкие сценарии и пошаговые инструкции для конкретных задач.

**Применимость и обязанность соответствия.** Правила настоящего стандарта едины для всех репозиториев - хаба `project_standards` и производных проектов. Навык, создаваемый или редактируемый вне хаба (в производном репозитории), обязан соответствовать этому стандарту в той же полноте: обязательный frontmatter (`id`, `description`, `auto_apply`, `type`), структура разделов, именование файла, стиль и объем. Локальных исключений нет - производный репозиторий применяет стандарт как есть, без ослабления требований. Перед созданием или изменением файла в `doc/skills/` агент сверяется с настоящим документом.

Общие (`glob_*`) и хаб-навыки (`hub_*`) в производных репозиториях доступны только для чтения: их поддерживают в хабе и распространяют навыком `hub-sync-skills`, поэтому локальные правки будут затерты при синхронизации. Собственные проектные навыки репозитория создаются и редактируются локально с соблюдением требований настоящего стандарта.

## 01.01. Назначение навыка

*Обязательно.*

Навык - файл с инструкцией для AI-агента по одной специализированной задаче или workflow.

Примеры: синхронизация стандартов между проектами, развертывание по внутреннему чеклисту, генерация отчета в фиксированном формате.

Навык создавать только если сценарий:
- повторяется в проекте;
- требует доменных знаний, которых нет в общих правилах;
- описывается пошагово, с командами, путями или шаблонами.

## 01.02. Расположение файлов

*Обязательно.*

Каталог навыков - `doc/skills/`. Он имеет двухуровневую структуру:

- **Корень `doc/skills/`** - общие навыки, применимые к любому проекту. Эти навыки входят в универсальный набор и работают в любом репозитории. Plain-навыки корня именуются с префиксами `glob_` (общие) и `hub_` (хаб); в хабе `project_standards` все общие и хаб-навыки сейчас оформлены каталогами SKILL.md (формат Anthropic), плоских представителей в корне нет.
- **`doc/skills/<repo-name>/`** - проектные plain-навыки (слаг `pr_glob`, префикс `pg_`), применимые только к конкретному проекту. `<repo-name>` - имя папки репозитория (`Path.cwd().name`), одна подпапка на проект.

```
doc/skills/
├── pg-parse-report/           # проектный навык Anthropic (pg-, слаг pr_glob)
└── my_project/                # проектные plain-навыки репозитория
    └── pg_db_migrate.md       # проектный plain (pg_, слаг pr_glob)
data/skills/
├── pl-extract-emails/         # локальный навык Anthropic (pl-, слаг pr_loc, вне синхронизации)
└── extract_emails.md          # локальный plain-навык (слаг pr_loc, вне синхронизации)
```

**Правила:**

- Общие навыки размещать только в корне `doc/skills/` и именовать с префиксом `glob_` (слаг `hub_glob`).
- Проектные навыки (слаг `pr_glob`) размещать: плоские - в `doc/skills/<repo-name>/pg_<name>.md`, каталоги Anthropic - в `doc/skills/pg-<name>/`; `<repo-name>` - имя папки текущего репозитория.
- Хаб-навыки (служебные навыки хаба `project_standards`, которые не распространяются в производные репо) размещать только в корне `doc/skills/` хаба и именовать с префиксом `hub_` (слаг `hub_loc`, раздел 01.03).
- Общие (распространяемые) навыки размещать в корне `doc/skills/` и именовать с префиксом `glob_` (раздел 01.03); хаб раздает их во все репо навыком `hub-sync-skills`.
- Локальные навыки (слаг `pr_loc`) размещать только в `data/skills/`; допускаются оба формата: каталог `pl-<name>/SKILL.md` или без префикса `<name>/SKILL.md` (формат Anthropic) и плоский `pl_<name>.md` или без префикса `<name>.md` (plain-формат); в синхронизацию не входят (`skill_anthropic_standards.md`, раздел 01.03).
- Не создавать навыки в корне репозитория, в `src/` и других каталогах вне `doc/skills/` и `data/skills/`.
- Папка `doc/skills/` опциональна - создавать только если в проекте предусмотрены навыки.
- Один навык - один файл `.md`. Структура внутри уровня (корень или подпапка проекта) - плоская: без вложенных `scripts/`, без вложенных `SKILL.md` (правило plain-формата; каталоги с `SKILL.md` формата Anthropic - см. `skill_anthropic_standards.md`).
- Имя проектной подпапки - всегда в нижнем регистре, совпадает с именем папки репозитория.
- При миграции плоского навыка в формат Anthropic плоский файл перемещается в `templates/` каталога навыка и остается каноном пары; правила пары форматов - `skill_anthropic_standards.md`, раздел 01.03.

**Почему `doc/skills/` как единая точка хранения:**

- навыки копируются в новые проекты вместе с шаблоном;
- не привязаны к конкретному инструменту или агенту;
- версионируются в git вместе с доменной логикой проекта;
- служебные каталоги инструментов остаются только для локальных настроек среды.

**Каталог-агрегатор.** Центральный репозиторий `project_standards` служит хабом каталога навыков: навык `hub-sync-skills` собирает навыки из всех репозиториев в `project_standards/doc/skills/ext/<repo-name>/` для единого обзора. Общие навыки (корень `project_standards/doc/skills/`) поддерживаются вручную как каноничные.

**Большие навыки:** если материал превышает ориентир объема (раздел 02.02), разбить сценарий на несколько файлов в `doc/skills/` (или в `doc/skills/<repo-name>/` для проектных) или вынести код и шаблоны в `run/`, `doc/specs/` - в теле навыка оставить ссылку и команду вызова.

## 01.03. Именование файлов

*Обязательно.*

| Правило | Пример |
| ------- | ------ |
| Latin characters, `snake_case` | `deploy_docker.md` |
| Английские слова, без транслита русских | `parse_report.md`, не `razbor_otcheta.md` |
| Расширение `.md` | `review_pr.md` |
| Имя отражает задачу, не общие слова | `deploy_docker.md`, не `helper.md` |
| Схема `{domain}_{action}` или `{action}_{object}` | `db_migrate.md`, `parse_report.md` |
| Без пробелов, без кириллицы в имени файла | `api_test_requests.md` |

Имя файла без расширения используется как идентификатор навыка (`id`) при ссылках в чате, frontmatter и документации.

**Типы навыков (таксономия).** Четыре типа навыков. Слаг и префикс - независимые сущности: слаг - канонический термин и значение поля `type` в frontmatter; префикс - маркер типа в имени файла или каталога.

| Тип | Слаг (`type`) | Префикс (плоский / каталог) | Расположение | Синхронизация |
| --- | ------------- | --------------------------- | ------------ | ------------- |
| Хаб-навык | `hub_loc` | `hub_` / `hub-` | корень `doc/skills/` хаба | только хаб |
| Общий навык | `hub_glob` | `glob_` / `glob-` | корень `doc/skills/` хаба | хаб -> все репо |
| Проектный навык | `pr_glob` | `pg_` / `pg-` | `doc/skills/<repo-name>/` (плоский) или `doc/skills/pg-<name>/` (Anthropic) | репо -> хаб (`ext/<repo-name>/`) |
| Локальный навык | `pr_loc` | `pl_` / `pl-` (опционален) | `data/skills/` (plain и Anthropic) | никуда |

Логика слага: первая часть - где истина навыка (`hub` - хаб, `pr` - репозиторий), вторая - охват (`loc` - локальный, `glob` - глобальный). Префикс - короткий маркер в имени: `pg` = project global, `pl` = project local. Тип навыка определяется префиксом имени; плоские файлы носят префикс с подчеркиванием (`hub_`, `glob_`, `pg_`, `pl_`), каталоги Anthropic - с дефисом (`hub-`, `glob-`, `pg-`, `pl-`). Исключение - локальные навыки (`pr_loc`): префикс опционален, имя без префикса допустимо.

**Категория - второй уровень префикса (у имени без префикса - первый сегмент).** После типового префикса в имени навыка может стоять категория - слаг области применения из закрытого справочника. Формат имени: плоский файл - `<prefix>_<category>_<name>`, каталог Anthropic - `<prefix>-<category>-<name>`; допустимо сокращение до `<prefix>_<category>` / `<prefix>-<category>`, когда имя навыка совпадает со слагом категории (`hub-update`). У локального навыка (`pr_loc`, префикс опционален) категория при имени без префикса занимает первый сегмент: плоский файл - `<category>_<name>`, каталог Anthropic - `<category>-<name>` (например, `cfg_kde.md` / `cfg-kde/`, категория `cfg`). Категория связывает имя навыка с полями frontmatter `category` и `category_name` (раздел 02.01.01) и совпадает с ними. Примеры: `glob-cfg-pip` (`cfg`), `glob-update-kilo-rules` (`update`), `pg_cfg_setup.md` (`pg_` + `cfg`).

| Слаг (`category`) | Название (`category_name`) |
| ----------------- | -------------------------- |
| `sync` | Синхронизация |
| `update` | Актуализация |
| `audit` | Аудит |
| `skill` | Навыки |
| `cfg` | Конфигурация |
| `rules` | Правила агентов |
| `agent` | Правила работы с агентом |
| `shell` | Настройки терминала |
| `alias` | Системные алиасы |
| `git` | Настройки GIT |
| `ssh` | Настройки SSH |

Справочник закрытый: слаг категории берется только из таблицы, `category_name` - только соответствующее ему название. Новый слаг добавляется правкой настоящего стандарта в хабе; локальные категории, синонимы и переименования названий не допускаются. Категория опциональна: без нее имя состоит из типового префикса и имени (`glob-<name>`, `pg_<name>.md`), поля `category` / `category_name` не заполняются, а второй сегмент имени не должен совпадать ни с одним слагом справочника (у локального навыка без типового префикса - первый сегмент). Тип навыка (раздел 01.03) и категория независимы: первый задает распространение и расположение, вторая - область применения.

Тип навыка фиксируется в его заголовке - обязательное поле `type` в YAML frontmatter (раздел 02.01.01). Поле проставляется при создании навыка, поддерживается актуальным при обновлении (при смене типа - обновляется), при миграции в формат Anthropic переносится в `metadata.type` (`skill_anthropic_standards.md`, раздел 02.01).

Для проектных навыков имя файла формируется так же (snake_case) с префиксом `pg_`, а размещается файл в `doc/skills/<repo-name>/`. Имя подпапки = имя папки репозитория (раздел 01.02).

**Префикс `hub_` для хаб-навыков (слаг `hub_loc`).** Навыки, которые работают только в хабе `project_standards` и не распространяются в производные репозитории (служебные навыки синхронизации и актуализации индексов), именуются с префиксом `hub_`: плоский файл `hub_<name>.md`, каталог формата Anthropic - `hub-<name>/`. Префикс визуально отделяет служебные навыки хаба от общих (распространяемых) и проектных. Навык `hub-sync-skills` определяет такие навыки по префиксу `hub_` (плюс сводный индекс `_index_skills_hub.md`) и не копирует их наружу.

**Индексы каталога навыков.** Каталог имеет три индекса: `_index_skills_hub.md` - сводный индекс хаба по всем навыкам всех репозиториев (только в хабе, ведет `hub-sync-indexes`); `_index_skills_repo.md` - локальный индекс навыков отдельного репозитория (в каждом не-хаб репо, генерируется навыком `glob-update-indexes`); `data/skills/_index_skills_pl.md` - индекс локальных навыков репозитория (генерируется тем же навыком `glob-update-indexes` при наличии `data/skills/`). Локальные навыки (`pr_loc`) в сводные индексы `_index_skills_hub.md` и `_index_skills_repo.md` не входят - они отражены в собственном `_index_skills_pl.md`. Индексные файлы (`_index_*.md`) навыками не являются и в реестры/сбор навыков не включаются.

**Префикс `glob_` для общих навыков (слаг `hub_glob`).** Навыки, которые раздаются из хаба во все производные репозитории, именуются с префиксом `glob_`: плоский файл `glob_<name>.md`, каталог формата Anthropic - `glob-<name>/`. Навык `hub-sync-skills` выгружает наружу файлы с префиксом `glob_` и каталоги навыков Anthropic с префиксом `glob-` и удаляет в приемниках устаревшие `glob_*.md` и `glob-*/`. В производных репозиториях эти файлы и каталоги доступны только для чтения (перезаписываются при синхронизации).

**Префиксы `pg_` и `pl_` / `pl-`.** Проектные навыки (слаг `pr_glob`) именуются с префиксом `pg_` (плоские, в `doc/skills/<repo-name>/`) или `pg-` (каталоги Anthropic, в корне `doc/skills/`); хаб агрегирует их в `doc/skills/ext/<repo-name>/` для инвентаризации. Локальные навыки (слаг `pr_loc`) живут только в `data/skills/` - вне каталога синхронизации; именуются с префиксом `pl_` (плоские) или `pl-` (каталоги Anthropic) либо без префикса. Итог: `hub_` / `hub-` - только хаб, `glob_` / `glob-` - раздается всем, `pg_` / `pg-` - репо -> хаб, `pl_` / `pl-` - локальный вне синхронизации. Имена без типового префикса не используются в `doc/skills/`: навык без префикса - кандидат на переименование (синхронизация выводит его в отчет); для локальных навыков `data/skills/` имя без префикса допустимо. Локальные навыки индексируются в `data/skills/_index_skills_pl.md` (`index_nav_standards.md`, раздел 06.02). Мигрированная пара форматов хранится и распространяется одним каталогом `glob-<name>/` - исходник plain-формата лежит внутри, в `templates/` (`skill_anthropic_standards.md`, раздел 01.03).

## 02.01. Структура файла навыка

*Обязательно.*

Каждый навык - один Markdown-файл. Разделы ниже - в указанном порядке. Пустые необязательные разделы не создавать.

### 02.01.01. YAML frontmatter (обязательно)

Блок метаданных в начале файла - обязателен. Используется для обнаружения навыка агентом и определения режима применения. Не заменяет раздел «Когда использовать», а дополняет его. Если frontmatter отсутствует, навык считается некорректным и не применяется.

```yaml
---
id: hub_sync_standards
type: hub_loc
category: sync
category_name: Синхронизация
description: Синхронизирует doc/standards/ с соседними проектами. Применять при запросах обновить, скопировать или синхронизировать стандарты
auto_apply: true
---
```

| Поле | Обязательность | Правило |
| ---- | -------------- | ------- |
| `id` | обязательно | Совпадает с именем файла без `.md` |
| `type` | обязательно | Слаг типа навыка из таксономии (раздел 01.03): `hub_loc`, `hub_glob`, `pr_glob`, `pr_loc`. Проставлять при создании; при обновлении поддерживать актуальным; при миграции в формат Anthropic переносить в `metadata.type` |
| `category` | опционально | Слаг категории (области применения) из закрытого справочника (раздел 01.03); второй уровень префикса имени (у имени без типового префикса - первый сегмент). Заполняется только парой с `category_name`; при миграции в формат Anthropic переносится в `metadata.category` |
| `category_name` | опционально | Название категории из справочника (раздел 01.03), соответствующее `category`; заполняется только парой. При миграции переносится в `metadata.category_name` |
| `description` | обязательно | Одна строка: что делает навык (WHAT) и когда применять (WHEN); третье лицо; ключевые слова из запросов пользователя |
| `auto_apply` | обязательно | `true` (по умолчанию) - навык применяется автоматически при совпадении запроса с разделом «Когда использовать»; `false` - только по явной ссылке `@doc/skills/` или упоминанию в `AGENTS.md`. Деструктивные навыки (удаление, перезапись, миграции БД) - всегда `false` |
| `version` | опционально | SemVer `X.Y.Z`; рекомендован для отслеживания изменений навыка |
| `status` | опционально | `draft` / `stable` / `deprecated`; дефолт `stable`. Если `deprecated` - навык не применяется |

### 02.01.02. Заголовок H1

Формат: `# Навык: <title>`

Пример: `# Навык: Синхронизация стандартов проекта`

### 02.01.03. Примечание (опционально)

Блок цитаты с ограничениями применимости - только для текущего репозитория, только для определенной роли, экспериментальный статус.

### 02.01.04. Описание

Заголовок: `## Описание`

Один абзац: что делает навык и какой результат ожидается.

### 02.01.05. Когда использовать

Заголовок: `## Когда использовать`

Список из 3-5 условий - когда агент должен применить навык. Формулировки конкретные, с ключевыми словами из реальных запросов пользователя.

Условия применения навыка - это не триггеры запуска действий. Триггеры запуска - только `ДЕЛАЙ` и `GO` (`project_standards.md`, раздел 07.02); отдельный раздел «Триггер-слова» в навыке не создается, словесные синонимы триггеров не выдумываются.

### 02.01.06. Предусловия (опционально)

Заголовок: `## Предусловия`

Что должно быть выполнено до начала: наличие файлов, ветки, переменных окружения, прав доступа. Указывать только если без этого навык не работает.

### 02.01.07. Инструкция

Заголовок: `## Инструкция` или `## Инструкция по применению`

Пошаговые действия для агента. Допускаются подразделы, нумерованные списки, блоки кода, чеклисты.

Уровень детализации инструкции выбирать по хрупкости задачи:

| Свобода агента | Когда | Как писать |
| -------------- | ----- | ---------- |
| Низкая | Миграции, деплой, синхронизация данных | Точные команды и порядок шагов, без альтернатив |
| Средняя | Отчеты, PR, генерация документов | Шаблон результата и допустимые отклонения |
| Высокая | Ревью, анализ, исследование | Принципы, чеклист, критерии качества |

### 02.01.08. Критерии завершения

Заголовок: `## Критерии завершения`

Явный список: по каким признакам агент считает задачу выполненной. Примеры: отчет пользователю, список измененных файлов, успешный exit code команды, заполненный шаблон.

### 02.01.09. Примеры (рекомендуется)

Заголовок: `## Примеры`

1-2 пары «запрос пользователя → ожидаемое действие или вывод». Помогает агенту и автору навыка проверить однозначность формулировок.

### 02.01.10. Дополнительные разделы (опционально)

По необходимости после основных разделов:
- `## Ограничения` - что не делать;
- `## Скрипт` или вложенный код в инструкции - готовый код для выполнения;
- `## Пример результата` - образец вывода или отчета.

Встроенный код в навыке - для коротких одноразовых сценариев. Если скрипт превышает ~100 строк, вынести в `run/` или `debug/` и в навыке указать только путь и команду запуска.

### 02.01.11. Root-команды и подтверждение выполнения (обязательно для навыков с привилегированными операциями)

Заголовок: `## Root-команды и подтверждение выполнения`

Навык, при применении которого выполняются привилегированные операции (изменение системных конфигов, установка пакетов, управление системными службами), обязан содержать этот раздел. Он описывает два пути применения и обязательные правила ожидания для агента; общий порядок привилегированных операций - `project_standards.md`, раздел 05.04, точечный оверрайд - раздел 01.01.02. Навык без привилегированных операций раздел не содержит.

Два пути применения привилегированных действий:

- штатный путь скрипта: при действующем проектном оверрайде 05.04, наличии askpass и графической сессии скрипт применяет изменения сам через `sudo -A`; агент не перекладывает эту работу на пользователя;
- ручной путь: если штатного пути нет, команды передаются пользователю; агент sudo сам не запускает.

Обязательные правила для агента:

- выдав пользователю команды, агент не считает их выполненными: он дожидается явного подтверждения пользователя либо объективной проверки состояния (повторный `recon` или `status`, чтение целевого файла или значения);
- до подтверждения или проверки агент не переходит к следующему элементу, следующему навыку и не завершает цикл;
- если состояние нельзя проверить без root, агент запрашивает подтверждение и точную команду проверки;
- итог по элементу (применен или не применен) агент сообщает только по подтвержденному или проверенному состоянию.

## 02.02. Содержание и стиль

*Обязательно.*

- Язык - русский (как в основном стандарте проекта)
- Текст - лаконичный, без эмодзи, без эмоциональных формулировок
- Использовать hyphen `-` вместо em-dash и en-dash
- Не использовать ellipsis (`...`, `…`)
- Пути - через `pathlib` или явные пути относительно `PROJECT_ROOT`, как в основном стандарте
- Команды и код - в fenced-блоках с указанием языка
- Не дублировать общие правила из `project_standards.md`, `AGENTS.md`, `CLAUDE.md`
- Терминология - одна на навык; не смешивать синонимы (endpoint / route / path и т.п.)
- Не упоминать конкретные навыки из конкретных репозиториев: имена чужих репо, пути `doc/skills/ext/<repo>/`, реальные проектные навыки соседей - запрещены. Только обобщенные примеры и плейсхолдеры: `<repo-name>`, `<name>`, `pg_<name>`, `pl-<name>`, `glob-<name>`. Ссылки на соседние навыки того же репозитория разрешены
- Плейсхолдеры - только латиницей (`<repo-name>`, `<name>`, `<dir-name>`); кириллица внутри угловых скобок запрещена (раздел 04.03 основного стандарта)

**Объем:** навык должен быть самодостаточным для выполнения задачи, но без лишних пояснений базовых вещей. Ориентир - до 800 строк в одном файле. Если материала больше - разбить на несколько навыков по отдельным задачам или вынести код и шаблоны за пределы файла навыка (раздел 01.02).

## 03.01. Применение навыка агентом

*Обязательно.*

### 03.01.01. Когда применять

Агент применяет навык когда:
- пользователь явно указал файл (`@doc/skills/hub-sync-standards/templates/hub_sync_standards.md`) или название навыка;
- запрос пользователя совпадает с разделом «Когда использовать» и `auto_apply: true` в frontmatter;
- в `AGENTS.md` проекта навык перечислен как рекомендуемый для сценария.

Если frontmatter отсутствует - навык считается некорректным, не применяется. Агент сообщает пользователю о проблеме и просит добавить frontmatter.

### 03.01.02. Приоритет при нескольких совпадениях

1. Явная `@`-ссылка пользователя на конкретный файл навыка
2. Навык из `AGENTS.md` с более узким совпадением с запросом
3. Автоматическое совпадение по разделу «Когда использовать»
4. При равной специфичности - уточнить у пользователя; не объединять инструкции из разных навыков в один workflow

### 03.01.03. Порядок выполнения

Агент читает файл навыка целиком и следует инструкции. Действия навыка не должны противоречить основному стандарту и подтвержденным пользователем ограничениям проекта.

Если навык предполагает изменение файлов проекта, а пользователь не указал его явно через `@` - действуют правила уточнения из основного стандарта (раздел 07.02, пакетный или интерактивный режим): уточнение, ожидание ответов, подтверждение перед правками.

## 03.02. Антипаттерны

*Обязательно.*

Избегать при создании и редактировании навыков:

| Антипаттерн | Правильно |
| ----------- | --------- |
| Несколько равноправных инструментов или библиотек | Один вариант по умолчанию; альтернатива только с явным условием переключения |

| Дублирование git, logging, SQL из основного стандарта | Ссылка на раздел стандарта или краткое «как в project_standards.md» |
| Time-sensitive правила («до августа 2025 используй API v1») | Актуальный метод; устаревшее - в отдельный архивный навык или раздел «Устаревшие паттерны» |
| Один навык на несколько несвязанных сценариев | Отдельный файл на каждый повторяющийся workflow |
| Длинный скрипт в теле навыка | Код в `run/` или `debug/`, в навыке - вызов |
| Размытые условия применения («когда нужна помощь») | Конкретные условия из реальных запросов пользователя |
| Раздел «Триггер-слова» или словесные синонимы триггеров запуска в навыке | Условия применения - в «Когда использовать»; триггеры запуска - только `ДЕЛАЙ` / `GO` (`project_standards.md` 07.02) |
| Навык с `auto_apply: true` для деструктивных операций | `auto_apply: false`; деструктивные действия только по явной `@`-ссылке пользователя |
| Упоминания конкретных навыков чужих репозиториев (имена репо, пути `doc/skills/ext/<repo>/`) | Обобщенные примеры и плейсхолдеры (`<repo-name>`, `pg_<name>`, `pl-<name>`); конкретика - только в индексах навыков |
| Плейсхолдеры кириллицей (`<имя-каталога>`) | Латиница: `<dir-name>`, `<repo-name>`, `<name>` (04.03 основного стандарта) |
| Навык с привилегированными операциями без раздела «Root-команды и подтверждение выполнения»; агент переходит к следующему элементу, не дождавшись подтверждения переданных команд | Обязательный раздел с двумя путями (`sudo -A` при оверрайде 05.04 / ручной) и правилами ожидания; итог - только по подтвержденному или проверенному состоянию (раздел 02.01.11, `project_standards.md` 05.04) |

## 04.02. Чеклист автора

*Обязательно.*

Перед публикацией навыка проверить:

- [ ] Один сценарий - один файл в `doc/skills/` (локальные - в `data/skills/`)
- [ ] Имя файла - `snake_case`, отражает задачу; префикс типа обязателен: `hub_`, `glob_`, `pg_` (для Anthropic-каталогов - `hub-`, `glob-`, `pg-`); для локальных навыков `data/skills/` - `pl_` / `pl-` или без префикса
- [ ] Frontmatter обязателен: `id`, `description`, `auto_apply`, `type` (все четыре поля заполнены); `type` - слаг типа из таксономии: `hub_loc`, `hub_glob`, `pr_glob`, `pr_loc`
- [ ] Категория: при наличии - слаг и название строго из закрытого справочника (раздел 01.03), второй сегмент имени совпадает со слагом (у локального навыка без типового префикса - первый сегмент), `category` и `category_name` заполнены парой; при отсутствии - соответствующий сегмент имени не совпадает ни с одним слагом справочника
- [ ] Нет упоминаний конкретных навыков чужих репозиториев и путей `doc/skills/ext/<repo>/` - только плейсхолдеры и обобщенные примеры
- [ ] Плейсхолдеры только латиницей, без кириллицы внутри угловых скобок
- [ ] Для деструктивных навыков - `auto_apply: false`
- [ ] Навык с привилегированными операциями содержит раздел «Root-команды и подтверждение выполнения» (два пути, ожидание подтверждения или объективной проверки до перехода дальше, итог только по проверенному состоянию); навык без таких операций раздел не содержит (раздел 02.01.11)
- [ ] (Опционально) `version` и/или `status` заполнены
- [ ] «Когда использовать» - 3-5 конкретных условий применения (не триггеры запуска; те - только `ДЕЛАЙ` / `GO`)
- [ ] «Критерии завершения» - явные признаки успеха
- [ ] Инструкция соответствует уровню свободы задачи (раздел 02.01.07)
- [ ] Нет дублирования общих правил из `project_standards.md`
- [ ] Объем до 800 строк или материал вынесен в `run/`, `doc/specs/`
- [ ] Навык отражен в индексе: `_index_skills_repo.md` (или `_index_skills_hub.md` в хабе) через `glob-update-indexes` / `hub-sync-indexes`; локальный навык `data/skills/` - в `data/skills/_index_skills_pl.md` через `glob-update-indexes`
- [ ] Если навык создается в производном репо - соответствие `skill_plain_standards.md` проверено в полной мере (frontmatter, структура, именование, стиль); общие и хаб-навыки локально не редактировались

Навык без корректного frontmatter не применяется автоматически.

## 05.02. Версионирование

Версионирование пакета стандартов - единое для всех документов пакета. Политика версионирования, реестр и карта маршрутизации - в `doc/standards/_index_standards.md`. Bump версии пакета - только по явному запросу пользователя (см. _index_standards.md).
