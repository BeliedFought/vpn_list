# Стандарт веб-приложений. Версия 4.15.0

Документ описывает правила разработки и развертывания веб-приложений: бэкенд на FastAPI (uvicorn) и веб-сервер nginx с одним или несколькими фронтами. Часть I (разделы 01-04) - разработка и локальный запуск, часть II (разделы 05-13) - развертывание и связь. Является дополнением к `project_standards.md` и применяется поверх него. Все требования основного стандарта остаются в силе, кроме случаев, явно описанных в данном документе. Порядок принятия решений при отсутствии или неоднозначности нормы - `project_standards.md`, раздел 07.06.

# Часть I. Разработка

## 01. Область действия и архитектура

### 01.01. Назначение и применимость

*Обязательно при создании веб-приложения.*

- Предмет стандарта - веб-приложение: HTTP-бэкенд на Python (FastAPI) и веб-сервер nginx, обслуживающий один или несколько фронтов
- Стандарт применяется к репозиториям, содержащим каталог `web/` (раздел 02.01); для репозиториев без веб-подсистемы не применяется
- Требования основного стандарта действуют изнутри `web/` - точные адаптации перечислены в разделе 02.01; прочие требования (код, вывод, безопасность, git, рабочий процесс) применяются без изменений

### 01.02. Термины

*Обязательно.*

- **Бэкенд** - приложение FastAPI под uvicorn: единственный процесс обслуживания API для всех фронтов
- **Фронт** - экземпляр nginx (server block) с собственным портом, привязкой к интерфейсу, набором статики и шаблонов и списком проксируемых префиксов; бэкенд один - фронтов может быть несколько (раздел 07.04)
- Термины пакета - `project_standards.md`, раздел 08

### 01.03. Прод-топология

*Обязательно.*

Целевой образ развернутого приложения, единый для обеих моделей:

1. nginx - единственная точка входа: публикует 80 и 443; порт 80 - только ACME challenge и redirect на 443
2. TLS терминируется на nginx (раздел 08)
3. Бэкенд не доступен из сети напрямую: модель A - слушает `127.0.0.1:<port>`, модель B - порты не публикуются
4. Статику фронтов отдает nginx напрямую (раздел 07.03); API проксируется на бэкенд (раздел 07.02)
5. Бэкенд предоставляет health endpoint `GET /healthz` без аутентификации (раздел 03.02) - используется процедурами запуска и обновления

### 01.04. Модели развертывания

*Обязательно - выбрать одну модель на приложение.*

| Модель | Состав | Когда выбирать |
|--------|--------|----------------|
| A - хост | systemd-юнит бэкенда + nginx из пакетов хоста (разделы 05, 07, 08, 09.01) | Хост без Docker; минимум слоев |
| B - Docker | compose: контейнер бэкенда + nginx-контейнер в `docker_network` (раздел 06) | Хост уже на Docker-инфраструктуре |

Смешение моделей в одном приложении не допускается. Существующая Docker-инфраструктура хоста описана в `deploy_docker_standards.md`.

## 02. Структура репозитория

### 02.01. Автономная подсистема web

*Обязательно.*

Вся веб-подсистема проекта находится в каталоге `web/` и автономна: собственная конфигурация, секреты, данные, логи, SQL и tooling. Правила основного стандарта о корневых папках (`project_standards.md`, разделы 01.01, 01.02, 04.06) применяются изнутри `web/`: `config` -> `web/config`, рантайм-данные -> `web/var/` (раздел 02.07: переносимые - `web/var/user`, служебные - `web/var/system`), `sql` -> `web/sql`, точки входа `run` -> `web/run`, `.env` -> `web/.env`, `requirements.txt` -> `web/requirements.txt`, `requirements-dev.txt` -> `web/requirements-dev.txt`, `pyproject.toml` -> `web/pyproject.toml`, `uv.lock` -> `web/uv.lock`. В чисто веб-репозитории корневые `config/`, `data/`, `sql/`, `log/`, `var/`, `.env` не создаются. Размещение кода в `web/` вместо `src/` - осознанное отклонение от `project_standards.md` (раздел 01.01), зафиксированное этим документом.

```
web/                              # автономная веб-подсистема
├── __init__.py                   # пакет web
├── __main__.py                   # точка входа: чтение [web] из config.ini, запуск uvicorn
├── app.py                        # app factory: create_app()
├── routes/                       # роутеры: api_*.py (JSON API), page_*.py (SSR)
├── deps.py                       # зависимости FastAPI (авторизация, сессии БД)
├── health.py                     # GET /healthz (раздел 03.02)
├── localization.py               # i18n бэкенда (project_standards.md, 04.01)
├── config/
│   └── config.ini                # [app] обязателен, [web] - host, port, reload
├── .env                          # секреты (0600); не коммитится
├── .env.example                  # шаблон переменных без значений
├── requirements.txt              # зависимости приложения (пиннинг ==)
├── requirements-dev.txt          # ruff, mypy
├── uv.lock                       # локфайл транзитивных зависимостей; коммитится
├── pyproject.toml                # [tool.ruff], [tool.mypy]; без секций сборки
├── static/                       # статика фронта: css/, js/, img/
├── templates/                    # шаблоны Jinja2 (SSR)
├── var/                          # рантайм-данные (раздел 02.07); не коммитится
│   ├── user/                     # переносится, бэкапится: db/, upload/, export/, backup/, keys/, ext/
│   └── system/                   # машинно-локальное, воспроизводимое: log/, cache/, tmp/, state/, session/, static/
├── sql/
│   ├── ddl/                      # схема
│   ├── migrations/               # M<N>_<description>.sql (project_standards.md, 03.02.03)
│   ├── queries/, dml/
│   └── _index_sql.md
├── run/                          # CLI-скрипты: db_migrate.py и др. (project_standards.md, 03.03)
└── deploy/
    ├── nginx/<app>.conf          # шаблон server block (при нескольких фронтах - <front>.conf)
    ├── systemd/<app>.service     # шаблон юнита (модель A)
    └── docker/
        ├── Dockerfile            # образ бэкенда (модель B)
        ├── .dockerignore         # исключения из контекста сборки (06.01)
        └── docker-compose.yml    # модель B
```

- Каталог `.venv` и файл `.python-version` - в корне репозитория (`project_standards.md`, раздел 01.07); запуск - из корня репозитория
- Папки создаются только по факту использования: API-only проект - без `templates/`; проект без БД - без `sql/` и `var/user/db/`; модель A - без `deploy/docker/`
- Инициализация чисто веб-репозитория адаптирует шаги `project_standards.md` (раздел 07.03): структура подсистемы - по этому разделу (02.01), рантайм - `web/var/` (02.07), конфиг и секреты - в `web/`

### 02.02. Tooling

*Обязательно.*

- Зависимости приложения - `web/requirements.txt` с пиннингом `==` (`project_standards.md`, 01.06); dev-зависимости (ruff, mypy) - `web/requirements-dev.txt`; не смешивать requirements и dev-секции pyproject
- `web/uv.lock` - фиксация транзитивных зависимостей для воспроизводимости dev-окружения и сборок; коммитится. Команды деплоя используют `web/requirements.txt` (пиннинг `==`), а не локфайл
- Конфигурация ruff и mypy - в `web/pyproject.toml`, секции `[tool.ruff]`, `[tool.mypy]` (наборы и параметры - по `code_standards.md`, раздел 08); секции сборки в pyproject не добавляются - веб-приложение не пакет CLI
- Проверки перед коммитом - из каталога `web/`: `ruff check .` и `mypy .`

### 02.03. Одиночный фронт

*Обязательно - режим по умолчанию.*

По умолчанию у приложения один фронт: его ассеты - `web/static/` и `web/templates/`. Имя фронтов в конфигурации nginx - `<app>.conf` (раздел 07.01).

### 02.04. Несколько фронтов

*Опционально - только по явному решению пользователя.*

При вводе второго и последующих фронтов ассеты группируются по фронтам:

```
web/
└── fronts/
    ├── public/
    │   ├── static/               # статика фронта public
    │   └── templates/            # шаблоны фронта public
    └── local/
        ├── static/               # статика фронта local
        └── templates/            # шаблоны фронта local
```

- Имя фронта - латиница, kebab-case, отражает роль: `public`, `local`, `admin`
- При переходе к `fronts/` одиночные `web/static/` и `web/templates/` не оставляются; шаблоны nginx именуются `<front>.conf` (раздел 07.04)
- Каждый фронт описывается четверкой: имя, порт + привязка, TLS, список проксируемых префиксов (раздел 07.04)

### 02.05. Артефакты развертывания deploy

*Обязательно при деплое.*

- `web/deploy/` - источник артефактов развертывания; реальные конфигурации живут в системных местах: `/etc/nginx/sites-available/`, `/etc/systemd/system/`, на хосте модели B - в контейнере
- При изменении прод-конфигурации - обновить шаблон в `web/deploy/` тем же изменением; расхождение шаблона и прод-конфигурации не допускается
- Исполняемые скрипты деплоя в репозитории не создаются - процедуры описываются в документации сервиса (раздел 12.01)

### 02.06. Агентские папки репозитория

*Обязательно.*

`doc/`, `diag/`, `test/`, `debug/`, `tmp/` остаются на корне репозитория по `project_standards.md` (раздел 01.01) - они относятся к репозиторию, а не к веб-подсистеме, и в `web/` не переносятся. Обязательный `doc/specs/ui_spec.html` - про консольный вывод и API (раздел 12.03).

### 02.07. Рантайм-данные

*Обязательно.*

Все данные, которые приложение создает в процессе работы, размещаются в одном каталоге `web/var/` и делятся на два класса: `var/user/` - пользовательский рантайм (переносится и бэкапится), `var/system/` - служебный рантайм (машинно-локальное, воспроизводимое). Каталог `web/var/` не коммитится.

**Пользовательский рантайм `web/var/user/`:**

| Папка | Назначение | Примеры |
| --- | --- | --- |
| `db/` | Встроенные базы данных и локальные хранилища | SQLite приложения, локальная витрина, локальная очередь заданий, WAL-журналы рядом с БД |
| `upload/` | Пользовательские файлы (оригиналы) | документы, изображения, вложения, импортируемые наборы |
| `export/` | Сформированные для отдачи артефакты | отчеты, выгрузки, архивы, сгенерированные документы |
| `backup/` | Резервные копии данных приложения | дампы БД, снимки, копии перед миграцией |
| `keys/` | Ключи, без которых данные нечитаемы или невосстановимы | шифрование данных, подпись с привязкой к данным; права 700 |
| `ext/` | Установленные в рантайме расширения | плагины, темы, пользовательские шаблоны |

**Служебный рантайм `web/var/system/`:**

| Папка | Назначение | Примеры |
| --- | --- | --- |
| `log/` | Логи приложения | файлы логов, ротация `keep_last` |
| `cache/` | Воспроизводимый кэш | ответы, вычисления, миниатюры и производные медиа, индексы поиска, скачанные внешние артефакты и модели |
| `tmp/` | Временное и промежуточное | частичные загрузки, распаковка, промежуточные выгрузки; чистится по TTL и при старте |
| `state/` | Мелкое изменяемое состояние | блокировки, pid, счетчики, курсоры синхронизации, почтовая очередь |
| `session/` | Серверные сессии | при файловом хранении вместо БД |
| `static/` | Сгенерированная статика | собранные ассеты, коллекция статики, если отдается из файлов |

**Карта соответствия (чтобы не создавать новых папок):**

| Артефакт | Класс |
| --- | --- |
| media, attachments, входящие downloads | `user/upload/` (производные - `system/cache/`) |
| reports, generated, исходящие downloads | `user/export/` |
| snapshots, dumps | `user/backup/` |
| thumbnails, search-index, models, compiled | `system/cache/` |
| locks, pid, counters, spool | `system/state/` |
| themes, plugins | `user/ext/` |
| ключи сессий (эфемерные) | `system/session/` или `.env` |

Перечисленные подпапки - закрытый словарь: новый тип артефакта относится к ближайшей подпапке по карте соответствия, расширение словаря - только правкой этого документа, без проектных оверрайдов.

**Правила:**

- Один корень, один ключ конфига: `[paths] var_folder` (по умолчанию `var/` внутри `web/`); подпапки - производные от корня, отдельные ключи не вводятся
- Приложение идемпотентно создает нужные подпапки при старте; неиспользуемые не создаются
- Владелец `web/var/` - пользователь сервиса; на `user/keys/` - права 700
- `web/var/` целиком исключен из git (`.gitignore`)
- Docker (модель B): именованный том монтируется только под `var/user/`; `var/system/` остается внутри контейнера и воспроизводится при пересоздании; для сохранения файловых логов - отдельный том на `var/system/log/`
- Резервная копия: `var/user/` целиком, включая `keys/`, но без `var/user/backup/` (исключается, чтобы не плодить рекурсию); `var/system/` не бэкапится
- Перенос на другую машину с прежними данными: пакет - `var/user/` + `config/config.ini` + `.env`; `var/system/` создается заново
- Файловые серверные сессии (`system/session/`) допустимы только для однопроцессного развертывания; при нескольких воркерах сессии хранятся в БД или внешнем хранилище, иначе требуется общий том
- Права точки монтирования тома (модель B): владелец каталога рантайма задается при старте контейнера (entrypoint или `chown` шагом развертывания); приложение работает от непривилегированного пользователя
- `system/cache` и `system/tmp` допускается монтировать как tmpfs: данные регенерируемые, перезапуск контейнера они не переживают - это норма
- Миграция существующего веб-проекта на `var/`: `web/data` -> `web/var/user/db`, `web/data/backup` -> `web/var/user/backup`, `web/log` -> `web/var/system/log`; обновить ключ конфига и compose; перенос выполнять при остановленном сервисе
- Комбинированный проект (CLI + `web/`): каждая часть имеет собственный рантайм (CLI - корневые `data/`, `log/`; web - `web/var/`). Общая БД размещается ровно в одном месте - по решению спецификации проекта; дублирование не допускается
- Внешние СУБД (PostgreSQL, MySQL и другие) в `var/` не размещаются - у них собственный том или сервис; `user/db/` - только для встроенных БД
- Очистка: `tmp/` - при старте и по TTL, `cache/` - по TTL, `log/` - ротацией `keep_last` (`project_standards.md`, 04.06)
- В рантайм не попадают: код, шаблоны, исходная статика, `config/`, `.env`, SQL-миграции

## 03. Приложение

### 03.01. Каркас FastAPI

*Обязательно.*

- App factory: `web/app.py` экспортирует `create_app()` - конфигурация приложения собирается в фабрике, глобального объекта приложения нет
- Роутеры - в `web/routes/`: файлы `api_<domain>.py` - JSON API, `page_<domain>.py` - SSR-страницы (Jinja2 через `templates/`); иерархия имени - от общего к частному (`code_standards.md`, 02.01)
- Общие зависимости (авторизация, сессии БД) - в `web/deps.py` через `Depends`
- Именование, типизация, docstrings - по `code_standards.md` (разделы 02.01, 02.03, 02.04); ошибки - по 05.02 основного стандарта; валидация внешнего ввода - до использования (05.01)

### 03.02. Health endpoint

*Обязательно.*

- Маршрут `GET /healthz` - без аутентификации, ответ `200` с JSON `{"status": "ok", "version": "<APP_VERSION>"}`
- Используется: локальным запуском (04.01), процедурами обновления и отката (раздел 10), проверками после старта
- Бизнес-проверки (доступность БД) в `/healthz` не включаются - endpoint отвечает за живость процесса

### 03.03. Префиксы и доступ

*Обязательно.*

- Префикс `/api/` - публичный JSON API
- Префикс `/admin/` - защищенные маршруты; авторизация выполняется в приложении (`web/deps.py`)
- nginx не является границей безопасности: разделение фронтов (07.04) ограничивает периметр, но каждое защищенное приложение обязано проверять авторизацию само
- Код состояния HTTP: ошибки запроса - 4xx, ошибки приложения - 5xx; тело ошибки - одна строка, без сырого traceback

### 03.04. Конфигурация

*Обязательно.*

- `web/config/config.ini` по `project_standards.md` (01.02): секция `[app]` обязательна (name, version); секция `[web]` - `host`, `port`, `reload`
- Порт и host - только из конфигурации, не хардкодить; в модели B переменные окружения `WEB_HOST`, `WEB_PORT` переопределяют значения `[web]` (раздел 06.01)
- Секреты - только в `web/.env` (права 0600, `project_standards.md`, 05.01); `web/.env.example` ведется синхронно
- Корень веб-приложения (аналог PROJECT_ROOT) - каталог `web/`; вычисляется один раз в `web/app.py` от `__file__`, остальной код импортирует его (`project_standards.md`, 01.04)
- Рантайм-данные: ключ `[paths] var_folder` (по умолчанию `var/` внутри `web/`) задает единый корень рантайма (раздел 02.07); подпапки - производные от корня, отдельные ключи не вводятся

### 03.05. Graceful shutdown

*Обязательно.*

- Приложение корректно завершается по SIGTERM (`project_standards.md`, 05.03): uvicorn прекращает прием соединений и завершает активные запросы
- Lifespan shutdown освобождает ресурсы: закрытие соединений БД, файлов, фоновых задач
- systemd и Docker доставляют SIGTERM штатно; `Restart=on-failure` (05.02) не превращает штатную остановку в рестарт

### 03.06. База данных

*Обязательно при наличии БД.*

- SQL и миграции - по канону основного стандарта изнутри `web/`: `web/sql/` (ddl, queries, dml, migrations, `_index_sql.md`), миграции `M<N>_<description>.sql` с таблицей `schema_version` (`project_standards.md`, 03.02.03); DROP + CREATE на живых данных запрещен
- Служебные скрипты - в `web/run/`: `db_check_connection.py`, `db_check_schema.py`, `db_init.py`, `db_migrate.py` (`project_standards.md`, 03.03.01)
- Файл встроенной БД (SQLite) - в `web/var/user/db/` (раздел 02.07); путь берется от корня рантайма, не хардкодится
- Бэкап перед миграцией - обязательный шаг процедуры обновления (раздел 10.01)

## 04. Локальный запуск

### 04.01. Точка входа

*Обязательно.*

- Точка входа - `web/__main__.py`: читает `[web]` из `web/config/config.ini` и вызывает `uvicorn.run("web.app:create_app", factory=True, host=..., port=..., reload=...)`
- Запуск из корня репозитория: `.venv/bin/python -m web`
- Ключ `[web] reload = true` - только для разработки; в проде `false`
- Проверка после старта: `curl http://127.0.0.1:<port>/healthz`

### 04.02. Статика без nginx

*Обязательно.*

- В dev-режиме (`[web] reload = true`) приложение монтирует `web/static/` через `StaticFiles` - полный цикл работает без nginx
- В проде статику отдает nginx (раздел 07.03); одновременная раздача статики приложением и nginx не допускается

# Часть II. Деплой

## 05. Модель A (хост)

### 05.01. Размещение

*Обязательно.*

- Репозиторий размещается в `/opt/<app>/` (clone/pull от root; файлы - `root:root`)
- Исполнение - от выделенного системного пользователя `<app>` (`useradd --system --no-create-home <app>`); работа от root или личного пользователя не допускается
- Владение файлами - `root:root`; исключение - `web/var/` (рантайм-данные, раздел 02.07: `var/user/` и, при файловых логах, `var/system/log/`): владелец - пользователь `<app>` (назначить `chown`), сервис пишет туда от своего имени
- Виртуальное окружение - `/opt/<app>/.venv`; зависимости: `/opt/<app>/.venv/bin/pip install -r web/requirements.txt`

### 05.02. systemd-юнит

*Обязательно.*

Шаблон - `web/deploy/systemd/<app>.service`:

```ini
[Unit]
Description=<app> web service
After=network.target

[Service]
Type=simple
User=<app>
Group=<app>
WorkingDirectory=/opt/<app>
ExecStart=/opt/<app>/.venv/bin/python -m web
EnvironmentFile=/opt/<app>/web/.env
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

- `EnvironmentFile` подгружает секреты из `web/.env` (0600); секреты в юните не хранятся
- Установка: `cp web/deploy/systemd/<app>.service /etc/systemd/system/` -> `systemctl daemon-reload` -> `systemctl enable --now <app>`
- Управление: `start`, `stop`, `restart`, `status`; логи - `journalctl -u <app> -f` (раздел 11.01)

### 05.03. nginx на хосте

*Обязательно.*

- Конфиг фронта: `cp web/deploy/nginx/<app>.conf /etc/nginx/sites-available/` + symlink в `sites-enabled`
- Upstream бэкенда: `http://127.0.0.1:<port>` - порт из `[web]` конфигурации приложения
- Проверка и применение: `nginx -t` -> `systemctl reload nginx`

## 06. Модель B (Docker)

### 06.01. Compose приложения

*Обязательно.*

Compose-файл - `web/deploy/docker/docker-compose.yml`; образ собирается из исходников репозитория, поэтому compose живет в репо, а не в `~/.docker/<service>/` (осознанное отклонение от `deploy_docker_standards.md`, 01.01); правила томов (02.04), сети (01.03), публикации портов (02.06) и шаблона (02.01, 02.03) docker-стандарта применяются:

```yaml
services:
  <app>:
    image: <app>:latest
    build:
      context: ../..
      dockerfile: deploy/docker/Dockerfile
    container_name: <app>
    restart: unless-stopped
    environment:
      WEB_HOST: 0.0.0.0
    env_file:
      - ../../.env
    volumes:
      - <app>_user_vol:/srv/web/var/user
      - ../../config:/srv/web/config:ro
    networks:
      - docker_network

volumes:
  <app>_user_vol:
    name: <app>_user_vol

networks:
  docker_network:
    external: true
```

- Порты бэкенда не публикуются - nginx обращается по `container_name` (02.06, 01.03 docker-стандарта)
- Переносимые данные (`web/var/user`, раздел 02.07) - именованный том с явным `name:` (02.04 docker-стандарта); служебный рантайм `web/var/system` остается внутри контейнера; конфигурация - bind mount `:ro`
- `WEB_HOST=0.0.0.0` переопределяет `[web] host` - внутри контейнера бэкенд слушает все интерфейсы; наружу порт не выходит
- Секреты - через `env_file` из `web/.env`; в образ они не попадают за счет `web/.dockerignore` - файл исключается из build context

Dockerfile (`web/deploy/docker/Dockerfile`, build context - каталог `web/`):

```dockerfile
FROM python:3.14-slim
WORKDIR /srv
COPY requirements.txt /tmp/requirements.txt
RUN pip install --no-cache-dir -r /tmp/requirements.txt
COPY . /srv/web
CMD ["python", "-m", "web"]
```

Обязательный `web/.dockerignore` в корне build context: `COPY . /srv/web` копирует весь контекст, и без исключений `.env`, `var/` попадут в образ. Минимальный состав:

```
.env
var/
__pycache__/
.venv/
```

### 06.02. nginx-сервис

*Обязательно.*

nginx добавляется в тот же compose вторым сервисом:

```yaml
  <app>-nginx:
    image: nginx:<tag>
    container_name: <app>-nginx
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ../nginx/<app>.conf:/etc/nginx/conf.d/<app>.conf:ro
      - ./ssl:/etc/nginx/ssl:ro
    networks:
      - docker_network
```

- Публикация `80`/`443` без привязки `<host_ip>` - единственный штатный случай публикации на все интерфейсы (`deploy_docker_standards.md`, 02.06, 02.07)
- Проксирование: `proxy_pass http://<app>:<port>` - по `container_name` и внутреннему порту из `[web]`
- TLS-сертификаты - bind mount `:ro` из подпапки `deploy/docker/ssl/` (раздел 08)
- Порядок запуска сервисов управляется документацией, `depends_on` не используется (`deploy_docker_standards.md`, 01.04)

### 06.03. Порядок развертывания

*Обязательно.*

Порядок - по `deploy_docker_standards.md` (01.05): создать папки, подготовить `web/.env`, собрать образ (`docker compose build --pull`), запустить (`docker compose up -d`), проверить (`/healthz` через `docker exec` или curl на опубликованный порт nginx).

## 07. nginx

### 07.01. Шаблон server block

*Обязательно.*

Шаблон - `web/deploy/nginx/<app>.conf` (модель A - в `sites-available` + symlink; модель B - bind mount в `conf.d`):

```nginx
server {
    listen 80;
    server_name <domain>;

    location /.well-known/acme-challenge/ {
        root /var/www/html;
    }

    location / {
        return 301 https://$host$request_uri;
    }
}

server {
    listen 443 ssl;
    server_name <domain>;

    ssl_certificate     /etc/nginx/ssl/<app>.crt;
    ssl_certificate_key /etc/nginx/ssl/<app>.key;

    root /opt/<app>/web;
    client_max_body_size 10m;

    location /static/ {
        expires 7d;
        access_log off;
    }

    location / {
        proxy_pass http://127.0.0.1:<port>;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 5s;
        proxy_send_timeout 60s;
        proxy_read_timeout 60s;
    }
}
```

- Порт 80 - только ACME challenge (08.01) и redirect на 443
- Пути сертификатов и `root` адаптируются по модели: модель A - как в шаблоне; модель B - сертификаты `/etc/nginx/ssl/` (bind mount, 06.02), `root` - на путь статики внутри образа, API - `proxy_pass http://<app>:<port>`

### 07.02. Проксирование

*Обязательно.*

- Заголовки пробрасываются всегда: `Host`, `X-Real-IP`, `X-Forwarded-For`, `X-Forwarded-Proto`; приложение доверяет `X-Forwarded-*` только от адреса прокси
- Таймауты: `proxy_connect_timeout 5s`, `proxy_send_timeout` и `proxy_read_timeout` - по потребности API (дефолт 60s)
- `client_max_body_size` - по потребности API (дефолт 10m); при загрузке файлов - явное значение в документации сервиса

### 07.03. Статика

*Обязательно.*

- `root` указывает на каталог веб-подсистемы: запросы `/static/...` отображаются в `web/static/...` без участия бэкенда
- Кэширование: `expires 7d` для `/static/`; `access_log off` для статики
- Имена файлов статики при изменении содержимого меняются (хеш или версия в имени) - устаревший кэш клиентов не работает

### 07.04. Несколько фронтов

*Обязательно при нескольких фронтах.*

Каждому фронту - отдельный server block с четверкой: имя, порт + привязка (`listen <ip>:<port>`), TLS, `root` (свой набор статики из раздела 02.04) и список проксируемых префиксов. Типовая конфигурация «наружный + локальный»:

| Фронт | Слушает | Привязка | TLS | Root | Префиксы проксирования |
|-------|---------|----------|-----|------|------------------------|
| `public` | 443 | все интерфейсы | ACME (08.01) | `fronts/public/static` | `/api/` |
| `local` | 8443 | `127.0.0.1` или LAN-IP | self-signed (08.02) или HTTP в доверенной LAN | `fronts/local/static` | `/api/`, `/admin/` |

- Локальный фронт никогда не публикуется на все интерфейсы: изоляция обеспечивается привязкой и файрволом (раздел 09), авторизацией в приложении (03.03)
- Модель B: наружный фронт публикуется без привязки (`"443:443"`), локальный - с привязкой (`"<LAN_IP>:8443:8443"` или `"127.0.0.1:8443:8443"`), по правилам `deploy_docker_standards.md` (02.06)

## 08. TLS

### 08.01. VPS (ACME)

*Обязательно для публичного домена.*

- Сертификаты - Let's Encrypt через certbot: `certbot --nginx -d <domain>` (плагин обновляет конфиг автоматически) либо webroot-режим с сохранением шаблона 07.01
- Модель B: certbot выполняется в контейнере либо в webroot-режиме через volume; вариант и команды - по документации certbot, выбор фиксируется в спецификации проекта
- Автообновление - systemd timer certbot (`systemctl list-timers | grep certbot`); ручной crontab не создается
- До выпуска сертификата в шаблоне 07.01 допустимы пути self-signed (08.02) - после выпуска certbot заменяет их

### 08.02. LAN (self-signed)

*Обязательно для LAN без публичного домена.*

```bash
openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout /etc/nginx/ssl/<app>.key \
  -out /etc/nginx/ssl/<app>.crt \
  -subj "/CN=<app>.local"
chmod 600 /etc/nginx/ssl/<app>.key
```

- Срок 365 дней: перевыпуск - повтором команды; права на ключ - 600
- Доверие сертификату - ручной импорт на клиентах; без импорта браузер предупреждает. API-клиенты используют `verify` с путем к CA-сертификату; `verify=False` - только по правилам `project_standards.md` (раздел 05.01): с обоснованием и ограничением области применения

## 09. Файрвол

### 09.01. Модель A

*Обязательно.*

- ufw: правила - только `80/tcp`, `443/tcp` и SSH из доверенной подсети; каждое правило - с комментарием имени сервиса (`deploy_docker_standards.md`, 03.01):

```bash
ufw allow 80/tcp comment '<app> http'
ufw allow 443/tcp comment '<app> https'
```

- Порт бэкенда (127.0.0.1) наружу не открывается; локальный фронт (07.04) правила ufw не требует - изоляция привязкой `listen <ip>:`

### 09.02. Модель B

*Обязательно.*

- ufw на опубликованные порты Docker не действует (`deploy_docker_standards.md`, 02.06) - контроль доступа выполняется привязкой `<host_ip>` в строках `ports`
- Наружный фронт - `"80:80"`, `"443:443"` без привязки; локальный - `"<LAN_IP>:8443:8443"` или `"127.0.0.1:8443:8443"`; правила ufw для них не создаются

## 10. Обновление и откат

### 10.01. Последовательность обновления

*Обязательно - шаги не пропускать и не менять местами.*

1. Бэкап данных: `pg_dump` для СУБД либо копия файла SQLite - модель A: копия в `web/var/user/backup/`; модель B: копирование из тома `var/user` (`docker exec` с `sqlite3 .backup` либо `docker cp`). Состав копии - `var/user/` без `backup/` (раздел 02.07)
2. Обновление кода: `git pull` в `/opt/<app>/` (модель A) или `git pull` + `docker compose build --pull` (модель B)
3. Миграции: `web/run/db_migrate.py` (`project_standards.md`, 03.03.01)
4. Рестарт: `systemctl restart <app>` (модель A) или `docker compose up -d` (модель B)
5. Health-check: `curl http://127.0.0.1:<port>/healthz`; при ошибке - `journalctl -u <app>` или `docker compose logs`

Бэкап из шага 1 - условие отката (10.02); без успешного бэкапа обновление не начинать.

### 10.02. Откат

*Обязательно.*

- Откат кода: `git checkout <tag-or-commit>` + рестарт (шаг 4) + health-check (шаг 5)
- Миграции не откатываются автоматически: исправление схемы - только новой миграцией (`project_standards.md`, 03.02.03); откат на схему до миграции - восстановление БД из бэкапа шага 1
- Zero-downtime вне области стандарта: короткий простой при рестарте допустим

## 12. Документация сервиса

### 12.01. Шаблон документа

*Обязательно.*

Каждое развернутое приложение описывается отдельным документом по образцу `deploy_docker_standards.md` (05.01), адаптированным для веб:

1. **Заголовок** (`# <app>`) + краткое описание (1-2 предложения): модель, порты, домены
2. **Подготовка** (опционально, перед «Установка») - пакеты, пользователь, БД, сертификаты
3. **Установка** - размещение репозитория, venv, юнит, nginx, файрвол - командами из шаблонов `web/deploy/`
4. **Расположение** - пути на хосте: репозиторий, venv, конфигурация nginx, юнит, данные
5. **Управление** - запуск, остановка, статус, логи, обновление (последовательность 10.01)
6. **Файрвол** - фактические правила ufw или привязки портов (09.01, 09.02)
7. **Базовая настройка** (опционально, после «Файрвол») - первичная конфигурация после запуска
8. **Конфигурация** (опционально) - тюнинг и расширенные опции
9. **Проверка** - health-check, `curl`, просмотр логов

Порядок секций и правило корневого уровня (`##` - только стандартные секции) - как в `deploy_docker_standards.md` (05.01, 05.02).

### 12.02. Граница с deploy-семейством

*Обязательно.*

- `deploy_standards.md`, `deploy_lin_standards.md`, `deploy_win_standards.md` к веб-приложениям не применяются: их предмет - установка Python-проекта как CLI-инструмента через `uv tool`
- Скрипты `install.py`/`update.py` в веб-репозиториях не канонизируются: процедуры деплоя и обновления - только в документации сервиса (12.01)
- Проект, совмещающий устанавливаемый CLI-инструмент и веб-подсистему `web/` в одном репозитории: к CLI-части и упаковке применяется deploy-семейство, к подсистеме `web/` - этот документ; граница - каталог `web/`. Стык и порядок фиксируются в спецификации проекта (12.01)
- Рантайм CLI-части (корневые `data/`, `log/`, `output/`) и рантайм веб-части (`web/var/`) - разные сущности: каждая часть ведет собственные данные, общая БД размещается ровно в одном месте (раздел 02.07)
- Прод-`web/config/config.ini` и `web/.env` не коммитятся - исключения в `.gitignore` подсистемы `web/`; прод-значения живут только на хосте, `git pull` (шаг 2 последовательности 10.01) с ними не конфликтует
- При изменении набора ключей `web/config/config.ini` или `web/.env` - миграция прод-файлов в рамках шага 2 последовательности 10.01 по канону `deploy_standards.md` (раздел 04.01): новые ключи - из example, значения пользователя сохранить

### 12.03. ui_spec.html

*Обязательно.*

- `doc/specs/ui_spec.html` обязателен для веб-репозитория с пользовательским выводом - по области действия `console_ui_standards.md` 01.02
- В веб-репозитории макет покрывает: вывод при локальном запуске и в `web/run/`-скриптах, формат лога, примеры API-ответов (примеры - `sample/api_*.json`)
